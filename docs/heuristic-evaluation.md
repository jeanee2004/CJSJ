## 2. 잘한 점 (2030 관점에서 특히 좋은 것)

### 2-1. "믿을 수 있다"는 느낌을 주는 장치가 많다
- 모든 제도에 **공식 확인 ✓ / 언론 인용 ◐ / 확인 필요 !** 배지와 기준일이 붙어 있다. 2030은 "블로그 정보 믿었다가 손해 본" 경험이 많아서 출처를 매우 중요하게 본다. 이 서비스의 가장 큰 강점이다.
- 실시간 카드에 "공공데이터 · 2026. 11. 4. 기준"이 붙어 있어 정보가 살아 있다는 신호를 준다.
- 푸터의 "이 서비스는 참고용이에요. 최종 판정은 각 기관에서 해요"는 과장하지 않는 태도로 신뢰를 높인다.

### 2-2. 진입 장벽이 낮다
- **로그인 없이 2분, 12문항**이라는 숫자를 첫 화면에 명확히 적었다. "얼마나 걸리는지"를 먼저 알려주는 건 2030이 시작 버튼을 누르게 만드는 가장 확실한 방법이다.
- 맛보기/심화 선택 화면이 카드 두 장으로 비교하기 쉽다(문항 수·시간·로그인 필요 여부).
- 문항마다 **"여쭤보는 이유"**가 있다. 소득·거주 같은 민감한 질문에 대한 거부감을 줄인다.
- "잘 모르겠어요" 선택지가 있어 모르는 게 부끄럽지 않게 해 준다.

### 2-3. 진짜 필요한 "함정"을 알려준다
- "잔금(집값의 마지막 지급)을 치르기 전에 신청해야 해요", "세종 임대료 지원과 국토부 월세지원은 둘 중 하나만", "다중주택은 대상에서 빠져요" 같은 내용은 다른 서비스에서 찾기 어렵다. 처음 집을 구하는 사람에게 실제 손해를 막아 주는 정보다.
- 건축물대장으로 **다중주택인지 주소로 바로 확인**하는 기능은 실용성이 높고 차별화된다.

### 2-4. 결과 화면이 "그래서 뭘 하면 되는데?"에 답한다
- 신청 가능 / 확인 필요 / 어려움 3단계로 나누고, 각 제도마다 **이유 + 다음에 할 일**을 적었다.
- 비교 기간(1·2·6년), 금리 낮게/높게 같은 조절 장치로 직접 따져 볼 수 있다.
- "몰랐다고 하신 지원 중에 받을 수 있는 게 있어요"처럼 내 답을 기억해 연결해 주는 문구가 개인화된 느낌을 준다.

### 2-5. 말투와 디자인 톤
- "~해요"체, 짧은 문장, 어려운 말 옆에 풀이(잔금 = 집값의 마지막 지급)가 일관되게 지켜진다.
- 남색 + 더스티 로즈의 차분한 색, 큰 외곽선 숫자(01·02·03), 큰 수치(119,738명 · 55.3%)는 2030이 익숙한 토스·당근 계열의 "정돈된 핀테크 톤"과 잘 맞는다. 관공서 사이트 느낌이 나지 않는 점이 좋다.
- 모바일에서 가로 스크롤이 생기지 않고(375px 기준 확인), 전체 메뉴가 큰 글씨로 잘 정리돼 있다.

## 3. 개선할 점 (심각도 순)

### 🔴 심각도 4 — 신뢰를 깎는 정보 불일치 (휴리스틱 4·2)

같은 제도에 대해 화면마다 다른 값이 적혀 있다. 출처를 강점으로 내세운 서비스라 더 치명적이다.

| 항목 | 홈 화면 | 결과 화면 |
|---|---|---|
| 세종 청년 주거임대료 지원 접수 | "2026.06.01~2026.06.30에 끝났어요" | "1년에 사흘만 접수해요(2026년은 3.3~3.5)" |
| 국토부 청년월세 접수 | "2026.03.02~2026.05.30" | "2026년 신규 접수는 5.29 마감" |
| 이자지원 문의 전화 | 044-300-6033 | ☎1533-1934 |
| 심화 설문 문항 수 | "35문항" | "12 / 34문항 응답" |

- **개선**: 일정·전화번호·문항 수를 한 곳(예: `eligibility.ts`·`survey` 데이터)에서만 정의하고 모든 화면이 그 값을 쓰게 한다. `nextplan.md`에도 적혀 있듯 결과 화면에 고정 문구("3.3~3.5", "5.29 마감")가 남아 있는 것이 원인으로 보인다.
- 출처가 서로 다를 때는 지금처럼 "보도 8,000만원 vs 정부24 7,000만원"으로 **차이를 드러내는 방식**을 모든 항목에 적용한다.

### 🔴 심각도 3 — 결과 첫 문장이 실제보다 좋게 들린다 (휴리스틱 1·2)
- 시험 응답 결과 제목이 **"받을 수 있는 지원이 2개 있어요"**였지만, 실제로는 신청 가능 1개 + 확인 필요 1개였고 그 확인 필요 1개는 **"마감"** 상태였다. 그리고 "추천 순서 1순위"는 위 2개가 아닌 "보증료 지원(확인 필요)"이었다.
- 2030은 첫 문장을 보고 기대했다가 아래에서 "마감"을 보면 **"낚였다"**고 느끼고 이탈한다.
- **개선**:
  - 제목은 "지금 바로 신청할 수 있는 지원 1개, 확인해 볼 지원 1개"처럼 상태별로 나눠 말한다.
  - 마감된 제도는 개수에서 빼거나 "다음 공고 대기"로 따로 묶는다.
  - 1순위 추천은 "신청할 수 있어요" 제도가 먼저 오도록 정렬 규칙을 다시 본다.

### 🟠 심각도 3 — "의견 보내기"가 실제로는 보내지지 않는다 (휴리스틱 1·5)
- 의견 남기기 팝업 안내에 "체험 단계라 지금은 이 기기에만 저장돼요"라고 적혀 있는데 버튼은 **"의견 보내기"**다. 사용자는 보냈다고 믿는다.
- **개선**: 서버 저장 전까지는 버튼을 "이 기기에 저장" 등으로 바꾸거나, Supabase 테이블이 준비되면 실제 전송 후 "보냈어요, 고마워요" 확인을 보여준다.

### 🟠 심각도 3 — 비로그인 결과가 새로고침하면 사라진다 (휴리스틱 3)
- "로그인하지 않으면 이 결과는 화면을 닫거나 새로고침할 때 사라져요." 2030은 결과를 캡처하거나 친구·연인에게 보내는 경우가 많은데, 2분 투자한 결과가 날아가면 다시 오지 않는다.
- 단, 홈에 "지난 결과 보기" 버튼이 있어 안내와 동작이 맞는지 확인이 필요하다.
- **개선**:
  - 비로그인도 이 기기(localStorage)에 최근 결과 1개는 보관하고, 안내 문구를 동작에 맞게 고친다.
  - **결과 공유 링크 / 이미지로 저장** 버튼을 추가한다. (신혼부부는 배우자와 함께 봐야 해서 특히 중요)
  - 로그인 유도는 "저장하려면 로그인"보다 "카카오로 3초 만에 저장"처럼 가볍게.

### 🟠 심각도 3 — 홈이 너무 길고 무겁다 (휴리스틱 8)
- 홈 페이지 높이: 데스크톱 약 7,400px, 모바일 약 8,900px. 로딩 화면 → 영상 히어로 → 두 번째 히어로 → 이용 방법 → 실시간 카드 → 제도 9개 → 통계 순서라 **설문 버튼까지 가는 길에 히어로가 두 번** 나온다("청년이 머무는 곳" + "내 집으로 가는 길").
- 첫 방문에 내려받는 용량이 약 15MB(영상 3개 약 12.7MB, 카카오 폰트 5종 약 1.5MB, 로고 PNG 419KB). 모바일 데이터로 처음 들어오면 체감 속도가 느리다.
- 실시간 카드 슬라이더가 같은 카드를 두 번 반복 렌더링한다(무한 회전용 복제로 보이며, 스크린리더는 같은 내용을 두 번 읽는다).
- **개선**:
  - 히어로를 하나로 합치고, 첫 화면 안에 "내 상황 확인해 보기"가 보이게 한다.
  - 영상은 모바일에서 포스터 이미지만 먼저 보여주고 탭하면 재생, 영상 3개 → 1개로 줄이기.
  - 폰트 굵기 5종 → 2~3종, 로고는 WebP/SVG로.
  - 제도 9개 전체 목록은 홈에서 3개만 보여주고 "전체 보기"로 분리.

### 🟡 심각도 2 — 제도 카드에 공고 원문이 그대로 노출 (휴리스틱 2·8)
- "ㅇ (사업 대상)", "※ 대출기한 연장 시…", "市 4.1% 부담", "① 주택공급: …" 같은 공공 API 원문이 펼침 영역에 길게 나온다. "어려운 경제 용어 없이"라는 약속과 어긋난다.
- **개선**: 펼쳤을 때 먼저 **쉬운 요약 3줄**(누가 · 얼마 · 언제)을 보여주고, 원문은 "공고 원문 보기"로 한 번 더 접는다.

### 🟡 심각도 2 — 설문 '다음' 버튼이 이유 없이 꺼져 있다 (휴리스틱 9)
- 답을 하지 않으면 다음 버튼이 비활성화되지만 **어느 문항이 남았는지** 알려주지 않는다. 한 화면에 3문항이 있고 아래 문항은 스크롤해야 보여서, 모바일에서 특히 헷갈린다.
- **개선**: 버튼을 누를 수 있게 두고, 누르면 안 한 문항으로 스크롤 + 빨간 표시. 또는 버튼 위에 "2개 남았어요" 표시.

### 🟡 심각도 2 — 결과 화면에서 답을 고쳐 보기 어렵다 (휴리스틱 3·6·7)
- 2030은 "내가 월세가 아니라 전세면?", "결혼하면?" 같은 **가정 비교**를 많이 한다. 지금은 처음부터 다시 해야 한다.
- **개선**: "내 응답 요약"에서 항목을 눌러 바로 바꾸면 결과가 다시 계산되게 한다.

### 🟡 심각도 2 — 다시 찾아올 이유(알림)가 없다 (휴리스틱 7)
- 많은 제도가 "마감 · 다음 공고를 기다려야 해요" 상태인데, 결과에 "다음 접수 공고를 알림으로 챙기세요"라고만 하고 알림 기능은 없다.
- **개선**: "다음 공고 나오면 알려줘" 버튼(카카오 알림톡·이메일·캘린더 추가). 2030에게 가장 확실한 재방문 장치다.

### 🟢 심각도 1 — 작은 것들
- **접근성**: 이미지 6개 중 5개에 대체 텍스트(alt)가 없다. 12px 미만 글씨가 61곳 있다(출처 줄, 배지 등). 높이 32px 미만인 버튼·링크가 모바일에서 31개(권장 44px).
- **모바일 히어로**: 첫 로딩 애니메이션 중 제목과 부제가 잠깐 겹쳐 보인다(애니메이션이 끝나면 정상).
- **장식 겹침**: 모바일에서 나비 장식이 "▶ 영상 재생" 버튼을 일부 가린다.
- **상단 메뉴**: "04 내 상황 확인 / 05 의견 남기기"는 링크가 아닌 팝업 버튼이라 주소를 공유하거나 새 탭으로 열 수 없다. `/#survey` 같은 주소를 주면 좋다.
- **용어 검색 버튼**: 돋보기 아이콘만 보고는 "용어 사전·가이드북"인지 알기 어렵다. 처음 한 번은 "모르는 말 검색" 같은 말풍선을 띄우면 좋다.
- **로딩 화면**: "LOADING" 화면이 매 방문마다 나오면 지루하다. 첫 방문에만 보여주거나 "건너뛰기"를 더 눈에 띄게.

## 6. 관리자 대시보드 구축 피드백

### 6-1. 지금 만들어진 것 (코드 기준)

| 구분 | 내용 |
|---|---|
| 요약 카드 | 방문 세션, 설문 시작, 맛보기/심화 완료율, 평균 체류 |
| 차트 | 일별 추이(방문·설문 시작), 섹션별 평균 체류, 버튼 클릭 순위 상위 10, 문항별 이탈, 응답 분포 4개(나이·소득·집 종류·점유 형태) |
| 자동 분석 | 규칙 기반 인사이트(이탈 문항, 맛보기→심화 전환, 주거비 부담 등)와 우선순위 개선 제안 |
| 내보내기 | 주간 리포트 복사·인쇄, CSV 내려받기(관리자 확인, 내려받기 기록) |
| 개인정보 | 가명 세션 ID만 저장, 5명 미만 집단 숨김, 표본 30 미만이면 경고 |
| 필터 | 기간 7일/30일/전체, 설문 종류 전체/맛보기/심화 |

**잘한 점**: 학생 프로젝트 수준을 넘는 설계다. 특히 ① 5명 미만은 숫자를 숨기고 표본이 적으면 경고하는 원칙, ② 숫자만 보여주지 않고 "그래서 무엇을 고칠지"까지 문장으로 뽑는 인사이트·제안, ③ 수집이 왜 안 되는지 진단해 주는 패널(연결 설정 → 테이블 → 권한 → 최근 24시간 수신)은 실제 운영 도구에서도 보기 드문 장점이다.

### 6-2. 먼저 막힌 것부터 (지금은 대시보드가 비어 있음)

1. **Supabase 테이블 만들기**: `001_init.sql`을 Supabase SQL Editor에서 실행해야 한다. 이게 안 되면 이벤트·응답이 하나도 저장되지 않는다.
2. **관리자 권한 주기**: 스키마를 실행하면 트리거가 관리자 이메일에 admin 권한을 준다.
3. **테스트 데이터**: 실제 사용자가 들어오기 전에 화면 배치를 확인할 수 있게 가짜 이벤트·응답을 수백 건 넣는 스크립트(`scripts/seed-demo.ts` 같은 것)를 두고, 확인이 끝나면 지운다.
4. **팀원 방문 빼기**: 지금은 팀원이 테스트로 들어온 방문도 똑같이 쌓인다. 초기에는 팀원 방문이 대부분이라 수치가 왜곡된다. `?internal=1`로 한 번 들어오면 그 기기를 내부 사용자로 표시하고 집계에서 빼는 방식을 추천한다.

### 6-3. 무엇을 볼지: 서비스 목표에 맞는 지표 정하기

지금 지표는 "얼마나 왔고, 설문을 얼마나 끝냈나"까지다. 하지만 이 서비스의 진짜 목표는 **"청년이 몰랐던 지원을 알게 되고 실제로 신청하러 가는 것"**이다. 그래서 가장 중요한 지표(북극성 지표)를 아래처럼 정하길 권한다.

> **북극성 지표: 결과 화면에서 "신청하기 / 공고 보기"를 누른 사람 수 (주간)**

이를 위한 전체 흐름(퍼널)은 다음과 같다. 지금은 ①~③만 추적하고 ④~⑦은 **추적하지 않는다.**

```
① 방문 → ② 설문 시작 → ③ 설문 완료 → ④ 결과 화면 조회
   → ⑤ 신청·공고 링크 클릭 → ⑥ 로그인/저장 → ⑦ 심화 설문 완료 → ⑧ 재방문
```

**추가할 이벤트 (`track.ts`의 `EventType`과 DB `check` 조건에 함께 추가)**

| 이벤트 | 언제 | `name`에 넣을 값 | 알 수 있는 것 |
|---|---|---|---|
| `result_view` | 결과 화면이 열릴 때 | `simple` / `deep` | 설문 완료 후 결과까지 도달률 |
| `apply_click` | "○○에서 신청하기", "공고 보기", "원문·신청 페이지" 클릭 | 제도 ID | **제도별 실제 관심도 (북극성)** |
| `result_status` | 결과 계산 직후 | 제도 ID + 상태(가능/확인/어려움) | 어떤 제도가 가장 많이 "가능"으로 나오나 |
| `share` | 결과 공유·저장(기능 추가 시) | 공유 방식 | 입소문 정도 |
| `glossary_search` | 용어 사전 검색 | 검색어(최대 20자) | 청년이 가장 모르는 용어 |
| `feedback_submit` | 의견 보내기 | 선택한 보기 코드 | 지금은 기기에만 저장돼 대시보드에 안 옴 |
| `address_check` | 다중주택 확인 실행 | 결과(다중주택/아님/실패) | 기능 사용률(주소는 저장하지 않음) |

또 `events.props`에 **유입 경로(referrer 도메인, `utm_source`)**를 넣으면 "인스타 홍보로 온 사람 vs 학교 공지로 온 사람" 중 누가 설문을 끝내는지 비교할 수 있다. 공모전·홍보를 하는 팀이라 이 지표가 특히 쓸모 있다.

### 6-4. 화면 구성 제안

한 페이지에 모든 차트를 늘어놓기보다 **질문 단위로 탭 3개**로 나누길 권한다.

**탭 1. 오늘의 요약 (매일 30초 확인용)**
- 요약 카드 5개 옆에 **지난 기간 대비 ▲▼ 변화**를 붙인다. 숫자 하나만 보면 좋은지 나쁜지 알 수 없다.
- 목표선 표시: 예) 맛보기 완료율 목표 70%, 결과→신청 클릭률 목표 30%.
- 기기별(모바일/데스크톱) 비율 — `device`는 이미 모으고 있는데 화면에 없다. 2030은 대부분 모바일이라 모바일 완료율을 따로 봐야 한다.

**탭 2. 사용성 (무엇을 고칠지)**
- 위 ①~⑧ 단계 퍼널을 한 줄로(단계별 남은 비율과 이탈 비율).
- 문항별 이탈(지금 있음) + **문항별 평균 응답 시간** — 오래 걸리는 문항이 어려운 문항이다.
- "잘 모르겠어요" 선택 비율이 높은 문항 순위 → 설명을 보강할 문항.
- 용어 검색어 순위 → 홈·결과 화면에 미리 풀어 쓸 단어.

**탭 3. 정책 인사이트 (발표·세종시 공유용)**
- **인지 격차 표**: 제도별로 "자격이 되는데 몰랐다고 답한 사람 비율". 코드에 `awarenessRank`(Q13 '몰랐다' 순위)가 이미 있으니 결과 판정과 엮기만 하면 된다. 이 표 하나가 "이 서비스가 왜 필요한가"를 가장 잘 보여준다.
- 제도별 "가능" 판정 수 vs 신청 클릭 수 → 관심은 있는데 클릭을 안 하는 제도는 안내 문구나 링크에 문제가 있다는 신호.
- 응답자 구성(나이·거주 형태·점유 형태·주거비 부담) — 지금의 분포 차트를 여기로 옮긴다.
- 주간 리포트(지금 있음)를 이 탭 맨 아래에 둔다.

**작은 화면 개선**
- 기간을 직접 고르는 달력(행사 전후 비교용)과 **이벤트 메모**(예: "11/10 인스타 홍보", "11/12 결과 화면 수정")를 일별 추이 그래프에 점으로 표시. 숫자가 왜 바뀌었는지 나중에 알 수 있다.
- 관리자는 휴대폰으로 볼 일이 많으니 요약 탭은 모바일 한 화면에 들어가게.

### 6-5. 기술 구조: 지금 방식의 한계와 다음 단계

| 지금 | 문제 | 추천 |
|---|---|---|
| 브라우저가 이벤트·응답을 각각 최대 5만 행 읽어 직접 계산 | 방문이 하루 수백 명만 돼도 몇 주 안에 한도에 닿고, 관리자 화면이 느려지고 오래된 기록이 빠진다 | Supabase에 **집계용 SQL 뷰/함수(RPC)**를 만들고 화면은 결과 숫자만 받는다. 예: `admin_daily_summary(from, to)`, `admin_funnel(survey_type)` |
| 매번 전체 기간 재계산 | 느림 | 하루 한 번 일별 요약 테이블(`daily_stats`)에 쌓기 (Supabase `pg_cron` 또는 Vercel Cron) |
| `events` 테이블에 누구나 아무 값이나 넣을 수 있음(`with check (true)`) | 장난·봇으로 수치 조작 가능 | 이벤트 이름 허용 목록 검사 트리거, 세션당 분당 입력 수 제한, 짧은 시간에 수백 건 들어온 세션은 집계에서 제외 |
| 의견 남기기는 기기에만 저장 | 대시보드에서 볼 수 없음 | `feedback` 테이블 추가(익명, 보기 코드만) |

**직접 만들 것과 외부 도구를 쓸 것을 나누기**
- 일반 방문 분석(방문 수, 유입 경로, 페이지별 이탈, 화면 녹화)은 직접 만들기보다 **Vercel Web Analytics**(배포처와 바로 연결)나 **PostHog**(무료 구간에서 퍼널·재방문·화면 녹화 제공)를 붙이는 게 빠르고 정확하다.
- 이 서비스만의 **설문·제도 판정·인지 격차** 분석은 지금처럼 직접 만든 대시보드가 맞다. 외부 도구로는 못 만든다.
- 즉, "방문 분석은 외부 도구, 정책 인사이트는 자체 대시보드"로 역할을 나누면 만들 양이 크게 줄어든다. 외부 도구를 붙일 때도 지금 원칙(이메일·IP 저장 안 함)을 유지하도록 IP 익명화 옵션을 켜고 개인정보처리방침에 적는다.

### 6-6. 대시보드 데이터를 2030 사용자에게도 돌려주기

모은 통계를 관리자만 보지 말고, 5명 미만 숨김 원칙을 지킨 채 **사용자 화면에도 보여주면** 2030 선호도가 올라간다. 비교·공감 콘텐츠는 이 연령대가 가장 많이 공유하는 유형이다.
- 결과 화면: "나와 같은 25~29세 응답자의 62%가 월세에 살아요", "이 지원을 몰랐던 사람이 71%예요".
- 홈의 "숫자로 보기": 공공 통계 옆에 "청정 세종 응답자 ○○명이 말한 가장 부담되는 비용 1위"처럼 실제 응답 데이터를 추가.
- 응답자가 30명 이상 모이기 전에는 표시하지 않도록 기존 `LOW_N` 기준을 그대로 쓴다.
